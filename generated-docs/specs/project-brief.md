## 1. Goal

Enable an Importer to upload bank-transaction CSV files into the system and an Approver to review, approve, reject, and export the resulting transactions, with a clear file-driven ingestion lifecycle and a per-transaction status flow that gates the available actions. Every imported transaction must reach a terminal state (Approved or Rejected), and rejections must carry an auditable note, reducing manual handling of bank transaction files for a financial-services back-office team.

## 7. Functional Requirements

Source: `requirements-2c.md` §6.1 (primary), `PrototypeBriefV2.md` §5 (corroborating).

- **R1:** The system accepts email and password for authentication via `POST /v1/auth/login` and routes the authenticated user to a role-specific landing surface (Importer → Upload/Dashboard; Approver → Transactions table).
- **R2:** The system displays an inline error state on login failure that distinguishes credential errors from connectivity/network errors.
- **R3:** The system accepts transaction file uploads for users with the Importer role via drag-and-drop or file picker, requiring `FileSettingId`, `FileSettingName`, and `FileName` parameters.
- **R4:** After a successful upload, the system creates a File Log entry and displays real-time upload progress, then shows explicit success or failure feedback.
- **R5:** The system displays a paginated, sortable table of File Logs with columns: File Name, Process Date, Record Count, and File Status; rows link through to that file's transactions.
- **R6:** The system displays a paginated, sortable table of Transactions with columns: Reference, Transaction Date, Account, Description, Amount, Currency, Transaction Type, and Status.
- **R7:** The system supports filtering the Transactions table by: Status (Imported / Approved / Rejected), File (FileLogId), Date range (calendar pickers), Amount range, and free-text search on Reference and Account Number.
- **R8:** The system supports filtering the File Logs table by: Status, File Name, and Process Date range.
- **R9:** An Approver may approve a Transaction in `Imported` status; the system transitions the status to `Approved` immediately after confirmation and displays a toast notification (auto-dismiss 4–8 s, top-right).
- **R10:** An Approver may reject a Transaction in `Imported` status by submitting a non-empty Rejection Note (stored as `UserNote`); the system transitions the status to `Rejected` immediately and displays a toast notification.
- **R11:** An Approver may export the currently-filtered set of Transactions as a CSV file named to reflect the active filter and date.
- **R12:** The system displays a per-File Summary view showing Total records, Imported count, Approved count, and Rejected count for a given File Log; clicking a count navigates to that filtered slice of the Transactions table.
- **R13:** An Importer may retry validation on a `Failed` File Log; the system re-attempts processing and updates the File Status.
- **R14:** An Importer may cancel a File Log, deactivating it and removing its Transactions from the Approver's working surface, subject to BR-07.
- **R15:** The system surfaces validation errors on a `Failed` File Log as a list of invalid rows with column metadata (from `/v1/files/validation-errors` and `/v1/files/validation-errors/columns`).
- **R16:** Both tables (Transactions and File Logs) use pagination with page-size options 5 / 10 / 20 / 50 (default 20); the pagination control is always rendered even when there is only one page.
- **R17:** Both tables support single-column sort, ascending on first click and descending on second; active sort column and direction are indicated in the header.
- **R18:** The system displays active filter chips for each applied filter with a Clear-all action; when zero results match the active filters, a no-results state is shown with the active chips and Clear-all visible.

## 8. Business Rules

Source: `requirements-2c.md` §6.2 (primary).

- **BR1:** When a Transaction's Status is not `Imported`, the Approve and Reject row-actions must be hidden in the UI — mutating actions are suppressed on terminal records, and a top-of-page banner names the terminal state. *(Severity: blocker)*
- **BR2:** When an Approver attempts to reject a Transaction, a non-empty Rejection Note must be provided; the submit control is disabled until a note is entered, and the note field validates on blur and on submit. *(Severity: blocker)*
- **BR3:** When an Approver approves or rejects a Transaction, a confirmation modal naming the transaction reference must be presented before the status change is committed; the primary action on destructive modals is styled destructively with default focus on Cancel. *(Severity: blocker)*
- **BR4:** When a File Log's File Status is `Processing` or `Uploaded`, the drill-down to its Transactions must indicate work-in-progress and the Transactions table must display a banner stating the dataset is not yet final. *(Severity: major)*
- **BR5:** When a File Log is in `Failed` status, the file detail view must surface the validation-errors view and the retry-validation control (visible to Importer only). *(Severity: major)*
- **BR6:** When an Approver triggers Export, the exported row-set must equal exactly the currently-applied filter set on the Transactions table; Export is disabled with a tooltip when zero rows match the current filter. *(Severity: blocker)*
- **BR7:** When a File Log has at least one `Approved` Transaction, the Cancel-File action must be blocked with an explanatory banner; the action is hidden from Approvers entirely. *(Severity: major)*
- **BR8:** When a Transaction's Status is `Rejected`, its Rejection Note (`UserNote`) must be visible on the Transaction detail in read-only form. *(Severity: major)*
- **BR9:** Approve and Reject row-actions are Approver-only; Importers see the Transactions table in read-only mode with no row-level action controls. *(Severity: blocker)*
- **BR10:** File Upload, Retry Validation, and Cancel File flows are Importer-only; Approvers do not see these controls in navigation or on file rows. *(Severity: blocker)*
- **BR11:** Empty states distinguish zero-data ("No file logs yet" / "No transactions yet" with the primary creation CTA) from zero-filter-results (active filter chips, Clear-all action, no creation CTA). *(Severity: major)*

## 9. Key Workflows

Source: `requirements-2c.md` §5 (task flows).

### Authentication

1. User opens the application unauthenticated — redirected to the login screen.
2. User enters email and password and submits.
3. On success: session cookie set; user routed to role-specific landing (Importer → Dashboard/File Logs; Approver → Transactions table).
4. On credential failure: inline error state distinguishing wrong credentials from network/connectivity failure.
5. On network failure: connectivity error state with a retry affordance.

### File Upload (Importer only)

1. Importer opens the Upload screen.
2. Selects a file via drag-and-drop dropzone or file-picker fallback.
3. Provides or confirms `FileSettingId`, `FileSettingName`, and `FileName`.
4. Confirms upload — system calls `POST /v1/files/upload`.
5. UI shows upload progress state.
6. On success: File Log created; status transitions through `Uploaded` → `Processing` → `Completed`; explicit success feedback shown.
7. On validation failure: File Status becomes `Failed`; validation-error count shown; retry-validation control offered.
8. On network failure: resumable error message with a retry control.

### File Log Overview (both roles)

1. User opens the Dashboard.
2. Paginated File Log table renders: File Name, Process Date, Record Count, File Status.
3. For `Completed` rows: row-click drills into that file's Transactions.
4. For `Failed` rows: retry-validation control visible to Importer; row is still drillable.
5. For `Processing` / `Uploaded` rows: in-progress state indicated; row is drillable but transactions table shows "not yet final" banner.
6. Empty state: "No file logs yet" with Upload CTA visible to Importer only.

### Retry Validation (Importer only)

1. Importer opens a `Failed` File Log's detail.
2. Reviews the validation-error rows.
3. Triggers Retry Validation — system calls `POST /v1/files/retry-validation?LogId={id}`.
4. On success: File Status transitions to `Completed`; transactions become available.
5. On continued failure: File Status remains `Failed` with updated error rows.

### Cancel File (Importer only — subject to BR7)

1. Importer opens a File Log's detail.
2. Triggers Cancel — system presents a destructive-action confirmation modal naming the file; default focus on Cancel (not Confirm).
3. On confirmation: `DELETE /v1/files?LogId={id}` called; File Log deactivated; Transactions removed from Approver's surface.
4. Blocked if any Transaction is `Approved` — explanatory banner shown instead of the modal.

### Transaction Review (Approver primary; Importer read-only)

1. User opens the Transactions screen (top-level or via file drill-down).
2. Applies filters as needed (status, file, date range, amount range, free text).
3. Active filter chips render with Clear-all.
4. Sorts columns as needed (single-column, ascending/descending).
5. For `Imported` rows (Approver only): Approve and Reject row-actions are available.
6. For `Approved` or `Rejected` rows: row-actions are hidden; terminal-state banner shown at page top.

### Approve Transaction (Approver only)

1. Approver clicks Approve on an `Imported` row.
2. Confirmation modal appears naming the transaction reference; primary action styled destructively; default focus on Cancel.
3. Approver confirms — system calls `POST /v1/transactions/approve?TransactionId={id}`.
4. Status flips to `Approved`; row updates immediately; toast notification (auto-dismiss 4–8 s, top-right).
5. On concurrent change (row already non-Imported): modal dismissed with banner explaining new state.

### Reject Transaction (Approver only)

1. Approver clicks Reject on an `Imported` row.
2. Modal opens with a mandatory Rejection Note (multi-line textarea with character counter).
3. Submit is disabled until a non-empty note is entered (validated on blur and on submit).
4. Approver submits — system calls `POST /v1/transactions/reject?TransactionId={id}` with `{ UserNote: "..." }`.
5. Status flips to `Rejected`; row updates immediately; toast notification.
6. On concurrent change: modal dismissed with banner.

### Export Transactions (Approver only)

1. Approver clicks Export in the Transactions toolbar.
2. CSV generated client-side from the currently-filtered transaction set.
3. File downloads with a name reflecting the active filters and date.
4. Export button is disabled (with tooltip) when zero rows match the current filter.

### File Summary (both roles)

1. User opens a File Log's detail (drill-down from File Log Overview).
2. Summary panel shows: Total records, Imported count, Approved count, Rejected count.
3. Clicking a count navigates to that filtered slice of the Transactions table.
4. If all Transactions are terminal, summary shows the completion state.
5. If File Log is `Failed`, summary panel shows a banner pointing to validation-errors view.
